## Context

См. `proposal.md` для мотивации изменения и delta-spec для наблюдаемого контракта. Сейчас `share-web` содержит одну страницу админки на Mantine, которая загружает один файл через presigned PUT, а `share-api` создаёт отдельный `UploadIntent` и `MediaJob` для каждого файла. Фоновый runner последовательно обновляет состояние медиа в SQLite, но клиент не имеет механизма автоматического обновления.

Нужно сохранить текущие границы безопасности: оригиналы и derivatives остаются в object storage, админские операции требуют активной сессии, ошибочные и неготовые медиа не становятся публичными, а опубликованный альбом нельзя редактировать через workflow состава.

## Goals / Non-Goals

**Goals:**

- Сделать админку рабочим пространством с выбором альбома, очередью загрузки и отдельной областью курирования.
- Надёжно провести пакет фотографий через загрузку, асинхронную обработку и автоматическое добавление готовых медиа в черновой альбом.
- Показывать переходы состояний без ручного refresh и не терять назначение альбома при перезагрузке страницы.
- Устранить дублирующиеся позиции и сделать ошибки сохранения исправимыми.
- Сохранить совместимость с существующими публичными маршрутами и приватностью медиа.

**Non-Goals:**

- Изменение публичной галереи, форматов derivatives или object-store протокола.
- Полноценное совместное редактирование несколькими администраторами.
- Автоматическая публикация альбома после завершения загрузки.
- Перенос обработки из текущего SQLite job runner в отдельную очередь.

## Decisions

### 1. Рабочее пространство вместо вертикального списка форм

Админка будет разделена на sidebar альбомов и основную область выбранного альбома. В основной области будут metadata альбома, зона мультизагрузки, очередь текущих файлов и сетка состава альбома. Для мобильной ширины sidebar станет верхним селектором, а действия сохранения останутся доступными после прокрутки.

Для превью новых файлов используются object URLs, созданные браузером. Для готовых медиа используются существующие authenticated `/media/:mediaId/:format/:width` маршруты; новый публичный media endpoint не нужен.

### 2. Один upload intent на файл, общее назначение альбома

Мультизагрузка остаётся набором независимых direct-to-storage операций: для каждого файла создаётся intent, выполняется presigned PUT и вызывается completion. Клиент ограничивает число параллельных операций до небольшого фиксированного значения и использует `Promise.allSettled`, чтобы ошибка одного файла не отменяла остальные.

В `UploadIntent` добавляются nullable `targetAlbumId`, `assignmentStatus` и безопасная `assignmentError`. `targetAlbumId` проверяется при создании intent и сохраняется как workflow-ссылка даже если альбом позднее удалён; это позволяет показать администратору, почему готовое медиа не было автоматически добавлено. Новая batch-сущность не нужна: пакет живёт в клиентской очереди, а надёжность назначения обеспечивается отдельным intent каждого файла.

Целевым может быть только неопубликованный альбом. После успешной обработки job runner в одной транзакции переводит медиа в `ready`, создаёт необходимые derivatives и, если целевой альбом всё ещё доступен для редактирования, создаёт `AlbumMedia` с безопасной следующей позицией. Если альбом опубликован или удалён, медиа остаётся готовым и приватным до ручного назначения в допустимый альбом, а intent получает терминальный статус назначения с безопасной причиной.

### 3. Live-обновление через условный polling

Для первой версии используется polling, а не WebSocket или SSE. Пока очередь содержит медиа в `pending` или `processing`, клиент раз в 2 секунды запрашивает админские статусы и состав выбранного альбома. После того как все элементы перешли в терминальное состояние, polling останавливается; при смене альбома или новой загрузке цикл запускается снова.

Это не добавляет новый persistent connection или dependency, использует SQLite как единый источник истины и переживает перезагрузку страницы. Один запрос обновляет статусы всех активных элементов, а UI сливает серверные значения с локальной очередью и не затирает ещё не отправленные файлы.

### 4. Порядок состава нормализуется сервером

UI отображает порядок через drag-and-drop и доступные кнопки перемещения, без ручного ввода произвольных чисел. Mutation состава принимает упорядоченный список медиа и `featured`, а сервер вычисляет позиции из порядка списка внутри транзакции. Это устраняет текущий сценарий, в котором удаление элемента и последующее добавление создают одинаковые позиции.

Сохранение разрешено только для неопубликованного альбома и готовых медиа. Сервер повторно проверяет эти условия независимо от UI. При ошибке транзакции старый состав сохраняется, а клиент показывает нормализованное сообщение и сохраняет локальный dirty-state.

### 5. Понятная модель состояний и ошибок

Клиент разделяет локальные этапы `queued`, `uploading` и `upload-failed` от серверных `pending`, `processing`, `ready` и `failed`. Известные безопасные коды (`media_not_ready`, `album_not_ready`, `album_must_be_unpublished`, ошибки intent и назначения) преобразуются в человекочитаемые сообщения; неизвестные ошибки получают общий безопасный fallback.

Публикация показывает имена медиа, блокирующих операцию, сопоставляя их с уже возвращёнными админскими данными. Сырые prompt-тексты, credentials, object keys и внутренние stack traces в UI не выводятся.

### 6. Аддитивная миграция и сохранение rollback-границы

Изменения SQLite добавляют nullable workflow-поля для уже существующих `UploadIntent`; исторические intent без назначения продолжают работать как ручные загрузки. Миграция не меняет существующие альбомы, media assets или derivatives. Сначала выкатывается схема и API, затем web-клиент; откат web-клиента безопасен, поскольку старый клиент игнорирует новые поля. Перед откатом API необходимо дождаться завершения активных назначений или обработать их как обычные готовые, но неназначенные медиа.

## Risks / Trade-offs

- [Polling создаёт лишние запросы] → запускать его только при активной очереди, обновлять одним запросом и останавливать после терминальных состояний.
- [Альбом могут опубликовать или удалить во время обработки] → проверять состояние в транзакции назначения, сохранять assignment status/error и не добавлять медиа в недоступный альбом.
- [Параллельные операции могут столкнуться на уникальной позиции] → вычислять позицию внутри транзакции, выполнять job runner последовательно и добавить проверку/retry для конфликта.
- [Один файл может истечь или не пройти direct upload] → обрабатывать элементы независимо, оставлять остальные в очереди, показывать retry и не создавать частично назначенную запись.
- [Authenticated preview может быть недоступен для неготового медиа] → использовать локальное превью до обработки, а серверное превью включать только после появления готового derivative.
- [Мультизагрузка увеличивает нагрузку на обработчик] → ограничить client-side concurrency и сохранить существующие лимиты размера, retry и lease job runner.
