# Дизайн: миграция с npm на pnpm

## Контекст

Монорепо сейчас работает на npm workspaces (корневой `package.json` объявляет шесть воркспейсов, корневой `overrides` пинит `@babel/core`, `packageManager: npm@11.19.0`). Внутренние пакеты ссылками вида `"config": "*"`, `"database": "*"`, `"tsconfig": "*"` — обратите внимание: воркспейс-пакет с именем `config` конфликтует по имени с посторонним публичным npm-пакетом. Оба продовых Dockerfile (`apps/share-api/Dockerfile`, `apps/share-web/Dockerfile`) устанавливают зависимости через `npm ci` по закоммиченному `package-lock.json`, а рантайм-стейдж share-api копирует этот локфайл плюс hoisted `node_modules` в финальный образ. `compose-dev.yaml` стартует API через workspace-флаги npm. Мотивация — см. proposal.md, раздел «Почему».

Ограничения, определяющие подход:

- Node запинен в `>=24.13.0 <25` (engines), образы — `node:24.13.0-bookworm-slim`; локально уже есть standalone-pnpm, Corepack не используется по требованию владельца.
- Здесь важны нативные сборки: sharp компилируется из исходников против системного libvips (сейчас — `npm explore sharp -- npm run build`), а tsx/tsup зависят от бинарников esbuild.
- Turbo (`turbo.json`) управляет всеми задачами и не зависит от пакетного менеджера; он остаётся без изменений.
- CI в репозитории нет; верификация локальная (`pnpm build/lint/typecheck/test`) плюс Docker-сборки.

## Цели / Не-цели

**Цели:**

- Единый воспроизводимый путь установки: `pnpm install --frozen-lockfile` везде (dev, Docker, compose).
- Сохранить точные версии зависимостей при миграции (без попутных обновлений).
- Все существующие скрипты и имена turbo-задач продолжают работать как есть.
- Оба Docker-образа собираются, dev-compose стек запускается.
- Ловить фантомные (необъявленные) импорты благодаря строгой структуре `node_modules` pnpm.

**Не-цели:**

- Обновление каких-либо runtime/dev-зависимостей сверх того, что сохраняет конвертация локфайла.
- Уменьшение рантайм-образа (мультистейдж-обрезка devDependencies, бандлы через `pnpm deploy`) — сначала паритет с текущей структурой.
- Введение CI-пайплайна, Renovate или настроек реестра (`.npmrc` для публикации).
- Изменения кода приложения, схемы Prisma или документированного поведения возможностей.

## Решения

### D1: Standalone pnpm с пином в `packageManager`, без Corepack

Корневой `package.json` получает `packageManager: "pnpm@12.0.0-rc.8"`. У контрибьютора достаточно любой standalone-установки pnpm ≥10: встроенный механизм manage-package-manager-versions сам скачает и использует запиненную версию внутри проекта. Corepack не используется вовсе (явное требование владельца репозитория).

- *Версия*: `12.0.0-rc.8` выбрана владельцем осознанно, несмотря на статус релиз-кандидата; локально уже стояла standalone-установка pnpm.
- *Почему вместо Corepack*: дрейф версий между контрибьюторами закрывается собственным механизмом pnpm без стороннего тулинга и его исторических проблем с ротацией ключей подписи.
- *Отклонённая альтернатива*: коммит pnpm как devDependency (`devDependencies: { pnpm }`) — циклические проблемы бутстрапа; активация через Corepack — отклонена владельцем.

### D2: Воркспейс и настройки pnpm живут в `pnpm-workspace.yaml`

Новый `pnpm-workspace.yaml` перечисляет те же шесть пакетов и содержит pnpm-специфичные настройки: `overrides` (переносит `@babel/core: 7.29.7` из корневого `package.json`) и `allowBuilds` (см. D5). Поле `workspaces` удаляется из корневого `package.json`.

- *Почему*: pnpm 10+ консолидирует конфигурацию здесь; один файл отвечает на вопрос «что pnpm знает об этом репозитории».
- *Альтернатива*: хранить overrides под `package.json#pnpm.overrides` — поддерживается, но разрывает pnpm-конфиг на два файла.

### D3: Конвертация локфайла через `pnpm import`, затем заморозка

Выполняется `pnpm import`, который выводит `pnpm-lock.yaml` из существующего `package-lock.json` (сохраняет resolved-версии и integrity-хэши), проверка свежим `pnpm install --frozen-lockfile`, затем `package-lock.json` удаляется.

- *Почему вместо ручной правки/переустановки с нуля*: гарантирует отсутствие тихих обновлений версий в миграционном коммите, оставляя дифф ревьюабельным («только смена тулинга»).
- *Альтернатива*: чистое переразрешение — отклонено; смешало бы смену пакетного менеджера с обновлением зависимостей.

### D4: Внутренние ссылки становятся `workspace:*`

Спецификаторы `"config": "*"`, `"database": "*"`, `"tsconfig": "*"` в потребляющих манифестах меняются на `"workspace:*"`.

- *Почему*: `"*"` матчится и с публичным пакетом реестра с именем `config`; `workspace:*` делает линковку локальных пакетов явной и громко падает, если воркспейс-пакет исчезнет, вместо тихого резолва из npm.
- *Альтернатива*: оставить `"*"` (pnpm всё равно линкует при совпадении диапазона с воркспейсом) — отклонено из-за неоднозначности коллизии имени `config`.

### D5: Явное разрешение нужных lifecycle-скриптов зависимостей

pnpm не запускает lifecycle-скрипты зависимостей без явного разрешения. В pnpm 12 механизм — карта `allowBuilds` (имя пакета → boolean) в `pnpm-workspace.yaml`; ключ `onlyBuiltDependencies` из pnpm 10–11 здесь больше не читается. Разрешены: `@prisma/client`, `@prisma/engines`, `better-sqlite3`, `esbuild`, `prisma`, `sharp`.

Отдельно: `better-sqlite3@13` собирается из исходников и вызывает `node-gyp`, который у него в devDependencies — транзитивно не ставится. Раньше это работало случайно (npm хоистил node-gyp из devDep-а share-api в корневой `.bin`), поэтому `node-gyp@12.4.0` объявлен явно в корневых devDependencies: корневой `.bin` входит в PATH lifecycle-скриптов у всех воркспейсов.

- *Почему явно, а не интерактивный `pnpm approve-builds`*: allowlist закоммичен и ревьюабелен; свежие клоны и Docker-сборки ведут себя одинаково, без промптов.

### D6: Dockerfile — frozen-установки, фильтры и закешированный Corepack

В обоих образах:

- `RUN npm install --global pnpm@12.0.0-rc.8` до установки (npm уже входит в node-образ), чтобы бинарник pnpm был запечён в слой; Corepack не используется.
- Build-стейджи: `pnpm install --frozen-lockfile` вместо `npm ci` (опциональные зависимости вроде платформенных пакетов sharp ставятся по умолчанию; старый флаг `--include=optional` аналога не требует).
- Все `npm run <script> --workspace <pkg>` превращаются в `pnpm --filter <pkg> <script>`; `npm exec --workspace share-api -- tsx …` — в `pnpm --filter share-api exec tsx …`.

Специфика share-api:

- Сборка sharp из исходников сохраняет окружение (`SHARP_FORCE_GLOBAL_LIBVIPS=1`, `npm_config_nodedir=/usr/local`). Вместо `npm explore sharp -- npm run build` путь к sharp резолвится внутри виртуального стора во время сборки, например `cd "$(find node_modules/.pnpm -maxdepth 1 -type d -name 'sharp@*')"/node_modules/sharp && pnpm run build` — glob, а не захардкоженный путь, потому что имена директорий `.pnpm` содержат peer-suffix хэши.
- Рантайм-стейдж копирует `pnpm-lock.yaml` и весь `/app/node_modules` (который содержит виртуальный стор `.pnpm`; симлинки pnpm относительные и переживают `COPY`), плюс тот же набор исходников воркспейсов, что и сегодня. `CMD` рантайма становится `pnpm --filter database db:migrate:deploy && exec node apps/share-api/dist/index.js` — валидно, потому что pnpm установлен глобально и в этом стейдже.
- `compose-dev.yaml` собирает `build`-таргет того же образа и переопределяет `command`; shell-строка переписывается теми же фильтрами.

Специфика share-web:

- `npm install --global turbo@2.10.10` остаётся (turbo распространяется standalone-бинарником; `pnpm dlx` отклонён — перекачивал бы на каждой сборке), затем `pnpm install --frozen-lockfile` и `pnpm --filter share-web build`.

### D7: Документация переводится на лексику pnpm

`AGENTS.md` (команды install/build/migrate, указания про локфайл) и два примера `import:legacy` в `docs/operations/storage-and-cutover.md` переходят с `npm [--workspace x]` на `pnpm [--filter x]`.

## Риски / компромиссы

- [Строгая изоляция вскроет необъявленные (фантомные) импорты в коде] → Прогнать полный цикл `lint`, `typecheck`, `build`, `test` после миграции; найденное чинить объявлением недостающей зависимости в нужном манифесте, а не ослаблением настроек (`shamefully-hoist` запрещён).
- [Заблокированные postinstall-скрипты тихо сломают esbuild/sharp/Prisma] → Allowlist из D5 закоммичен заранее; убедиться, что `pnpm install` не сообщает об ignored builds и `check:codecs` проходит.
- [`find`-резолв пути sharp может дать несколько совпадений] → Ограничить glob условиями `-maxdepth 1 -type d -name 'sharp@*'` и asserting ровно одного совпадения в шаге Dockerfile.
- [12.0.0-rc.8 — пре-релиз: возможны баги и изменения формата локфайла до стабилизации] → Пин точной версии везде (packageManager + Docker); откат пина на 11.22.0 при необходимости — вместе с регенерацией локфайла, так как формат между мажорами может отличаться; сбои всплывают сразу в локальных/Docker-сборках, а не при старте контейнера.
- [Рантайм-образ теперь содержит стор `.pnpm` рядом с symlink-структурой] → Тот же объём, что у сегодняшнего hoisted-дерева, с незначительной разницей на диске; оптимизация размера образа — явная не-цель.
- [Мышечная память контрибьюторов / устаревшие чекауты продолжают звать npm] → `AGENTS.md` обновляется в этом же изменении; `packageManager` + Corepack заставляет случайный `npm install` громко падать, а не форкать состояние локфайла; контрибьюторы однократно выполняют `pnpm install`.
- [Окно отката] → Миграция попадает одним сфокусированным коммитом; откат — `git revert`, возвращающий `package-lock.json` и npm-Dockerfile дословно.

## План миграции

Один PR, упорядоченный так, чтобы репозиторий никогда не оставался наполовину мигрированным:

1. Добавить `pnpm-workspace.yaml` (packages + overrides + onlyBuiltDependencies), почистить корневой `package.json`, переключить внутренние ссылки на `workspace:*`.
2. `pnpm import` → ревью сгенерированного `pnpm-lock.yaml` → удалить `package-lock.json`.
3. Переписать оба Dockerfile и `compose-dev.yaml`.
4. Обновить `AGENTS.md` и ops-документацию.
5. Верификация локально: свежий `pnpm install --frozen-lockfile`, `pnpm build`, `pnpm lint`, `pnpm typecheck`, тест-сьюты share-api, `docker build` обоих образов, smoke-тест `docker compose -f compose-dev.yaml up` (миграции + старт).
6. Смержить; контрибьюторы однократно выполняют `corepack enable && pnpm install`.

Откат: revert коммита.
